### Added

- Disk & the load pipeline (phase-07c — the game persists): saves reach disk and come back. `src/main/save-store.ts` (pure Node, directory injected — testable against real temp dirs) runs the exact `SAVE_FORMAT.md` §7.1 six-step atomic sequence, both `fsync`s included (the directory fsync is best-effort on Windows, recorded honestly — NTFS journals rename metadata), rotates `.bak`, and keeps the three newest `backups/` copies. **Crash safety by real interruption**: the sequence executes against a real directory and halts after each step — an existing good save survives every halt as one of the two real states, never a torn hybrid, and a first-save crash leaves a clean missing, not corruption. The load split is `ARCHITECTURE.md` §4.3 exactly: main does bytes → parsed JSON with `.bak` routing (both documents travel; `missing` only when neither file exists — present-but-unreadable is **never a silent new game**), and the renderer's pure `loadWorld` pipeline runs migration → validation → repair → hydration per candidate, with one deliberate exception: a newer save refuses outright and never falls back to an older backup. One save path, forward-built for 07e: every trigger arrives as main's `save:requested`; the renderer serializes at its single site (meta continuity — `createdAtUnixMs` forever, `saveCount` on success only, held quarantine written back) and main validates the document structurally on receipt before producing the canonical bytes itself (the renderer is untrusted, ADR-003 §3). Boot went async: new game only on truly-missing; unloadable saves stop with a clear in-overlay error; the load log lands in a devtools metric until 07e's summary. E2E on isolated profiles: save → relaunch → the _same_ farm continues (seed, creation time, tick, `.bak` all proven), and a hand-corrupted slot recovers from `.bak` live. Bonus repair rule found mid-milestone: an orphaned storage container becomes held stacks instead of a hydration crash. 799 unit/integration tests, 26 E2E
- Migration chain & validation (phase-07b): the mechanism ships before anything needs it — which is the point. `migrate.ts` is the one place `schemaVersion` is ever read (ADR-015 §2): `validateChain` fails a malformed chain at startup (gaps, skips, wrong start, stopping short — a build failure, never a player-facing one) and `runMigrations` returns typed results — newer saves refused outright, no-link versions corrupt, a throwing or version-lying link a `MigrationFailed` with the caller still holding the untouched original. Proven with a synthetic two-step chain plus non-destructiveness and determinism tests; `migrations/index.ts` ships empty and validated at v1. Validation lands in two layers: structural (`parseSaveDocument` — every field typed, grid encodings decoded so corrupt base64 is a typed error, never a hydration crash) and semantic (`repairSaveDocument`, non-destructive) implementing every `SAVE_FORMAT.md` §5.2 row under one principle — repair where unambiguous, drop where meaningless, **never delete player value** (the over-capacity inventory keeps every item, acceptance 11; behind-the-max allocator counters bumped — the ADR-015 §6 hazard as a repair rule). Unknown content is quarantined, not deleted (§5.3): the document gains a top-level `quarantine` section — present-and-empty from version 1, the `plugins: {}` reasoning — holding crops, buildings _with their storage_, owner-tagged stacks, and seed-bin memory; the same pass restores entries the moment their content returns and a safe home exists, deferring rather than destroying when it doesn't. - The save document & the round trip (phase-07a — save/load begins): `src/persistence/` opens with the version-1 document made real — `schema.ts` types `SaveDocument` field-for-field against the shipped `World` under the ADR-015 §1 header (`schemaVersion` first, `SAVE_MAGIC` second, `meta.createdAtUnixMs`), carrying everything the phase-0 sketch never anticipated: `cropStats`, `buildingStorage`, `lastPlanted`, the expansion counter, the allocator counters, and the workers' `energyTimer`/`replanTick` sub-period accumulators that continue-identically determinism demanded. The division of authority: ADR-002 (frozen) keeps the mechanism — JSON, atomic writes, the linear chain; `SAVE_FORMAT.md` keeps the field-by-field schema; ADR-015 owns the contract. Decides: a mandatory save identity header (`schemaVersion` first per ADR-002's frozen clause, the permanent `SAVE_MAGIC` constant second, `meta.createdAtUnixMs` set once at world creation); the three-version separation (save format / game / application versions independent — only the integer `schemaVersion` ever drives behavior, and a schema version is burned the moment its golden fixture is committed); migration governance (ordered registration validated at startup, deterministic links that never mutate their input, loading never writes so a partial migration structurally cannot exist on disk, and a pre-migration backup per schema version from v0.2 so even a wrong shipped migration destroys nothing); the full compatibility matrix (older = migrated forever, newer = refused never partially loaded, unknown core fields = ignored + logged, unknown content = quarantined, plugin data = preserved — user saves are user data, and invalidating any shipped save requires a successor ADR); the enumerated authoritative-state set for continue-identically restoration — including the catch that the ID allocator's counters must persist because `max + 1` reconstruction breaks determinism once `sellBuilding` has ever freed an ID, and that commands are deliberately not persisted (saves serialize at tick boundaries after the queue drains, ADR-010). - Economic simulation architecture (ADR-013): the canonical authority for every economy feature, phase-06 through v1.0+, authored under the freeze as its first sanctioned new decision (directive `fix/0.1/6.0ADR.md`). ## Versioning Rules

### Two version numbers

This project tracks **two independent versions**. Confusing them causes save-compatibility bugs.

| Version                 | Format                  | Meaning                     | Where                                   |
| ----------------------- | ----------------------- | --------------------------- | --------------------------------------- |
| **App version**         | Semantic (`0.1.0`)      | The release the player sees | `package.json`, `meta.gameVersion`      |
| **Save schema version** | Integer (`1`, `2`, `3`) | The persisted data format   | `schemaVersion` (`SAVE_FORMAT.md` §4.1) |

They move independently. A patch release may bump the schema; a minor release may not. **Only `schemaVersion` controls migration** — `meta.gameVersion` is informational and must never drive logic (`SAVE_FORMAT.md` §2.1).

### Semantic versioning, as applied here

Pre-1.0, the conventional rules are adapted to the roadmap in `PLAN.md`:

| Bump                | Means                                               | Example         |
| ------------------- | --------------------------------------------------- | --------------- |
| **MAJOR** (`1.0.0`) | v1.0 — the feature-complete life simulator          | Reserved        |
| **MINOR** (`0.2.0`) | A roadmap tier: new systems, possibly a schema bump | v0.1 → v0.2     |
| **PATCH** (`0.1.1`) | Fixes, balance, performance; no new systems         | Bug fix release |

**Backward compatibility is never broken**, at any bump (`AI_RULES.md` §1.4). A v0.1 save must load in v1.0. There is no version increment that licenses breaking a save.

## Entry Format

### Categories

Use these six, in this order. Omit empty ones.

| Category     | For                          |
| ------------ | ---------------------------- |
| `Added`      | New features                 |
| `Changed`    | Changes to existing behavior |
| `Deprecated` | Features to be removed later |
| `Removed`    | Features removed now         |
| `Fixed`      | Bug fixes                    |
| `Security`   | Vulnerability fixes          |

### Writing entries

Entries are for **players**, not developers. The reader wants to know what changed about the game, not which module was refactored.

```markdown
## [0.2.0] - 2026-XX-XX

### Added

- Weather system: rain automatically waters crops
- Plugin loader — mods can now add crops, items, and buildings
- Day/night cycle affecting worker schedules

### Changed

- Wheat growth time reduced from 120s to 100s
- Market Stall now sells at 92% (was 90%)

### Fixed

- Workers no longer stall when storage fills while carrying items
- Overlay re-docks correctly after a DPI change

### Save Compatibility

- Schema version 1 → 2 (adds weather state)
- v0.1 saves load automatically; no player action needed
```

### The Save Compatibility section

**Required on any release that bumps `schemaVersion`.** It must state the version transition and, in plain language, what the player needs to do — normally "nothing."

This section exists because save compatibility is the promise this project makes most seriously, and a release that changes the format without saying so undermines it even when the migration works.

### Rules

- **Player-facing language.** "Workers no longer stall when storage fills," not "fixed null deref in `deposit-task.ts`."
- **No internal refactors.** If it does not change what the player experiences, it does not belong here (that is what git history is for).
- **One line per change.** Link to an issue if there is detail worth having.
- **Add to `[Unreleased]` in the same commit as the change** (`AI_RULES.md` §5.4).
- **Balance changes are always listed.** A player who notices wheat is faster deserves to find it here.
- **Performance improvements are listed when measurable**, with the measurement: "Idle CPU reduced from 1.4% to 0.6%."

## Release Process

1. Verify every gate in `PLAN.md` §8 — **including zero known data-loss defects**
2. Move `[Unreleased]` entries under a new version heading with the release date
3. Add the Save Compatibility section if `schemaVersion` changed
4. Bump `version` in `package.json`
5. Confirm every golden fixture still loads (`SAVE_FORMAT.md` §4.4)
6. Tag the release `v<version>`
7. Create a fresh empty `[Unreleased]` section

Step 5 is not optional and not covered by step 1's general test run. It is the specific check that a released build can still load saves from every prior version.
