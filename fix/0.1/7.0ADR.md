==================================================
ADR-015 — Save Format Versioning & Migration
==================================================

Objective

Before implementing the Version 0.1 save system, formally define the irreversible architectural decisions surrounding save format, compatibility, versioning and migration.

This ADR establishes the long-term contract for every save file produced by the project.

Once Version 0.1 ships, save compatibility becomes a permanent responsibility.

This ADR exists to minimize future migration cost.

==================================================
Decision Required
==================================================

Determine and document:

• Save file identity
• Save format versioning
• Game version tracking
• Migration architecture
• Compatibility policy
• Serialization guarantees
• Deterministic restoration
• Failure handling
• Future extensibility

==================================================
Core Principles
==================================================

Save files are user data.

User saves must never be invalidated without an explicit documented reason.

Future versions should migrate saves whenever technically possible.

Gameplay code must never depend on save version.

Migration is a persistence concern only.

==================================================
Serialization Rules
==================================================

Define serialization principles.

Stable identifiers.

No runtime pointers.

No platform-specific objects.

No renderer state.

No Electron state.

No UI state.

Only deterministic gameplay state.

==================================================
Deterministic Restoration
==================================================

Loading a save must restore:

Simulation Tick

Workers

Resources

Containers

Buildings

Economy

Random Generator State

Commands (if applicable)

World State

Player State

Simulation should continue identically after loading.

==================================================
Future-Proofing
==================================================

Reserve extension points.

Future additions should require adding fields rather than replacing structures.

Unknown fields should be safely ignored whenever possible.

Avoid breaking existing save readers.

==================================================
Migration Framework
==================================================

Document how migration functions are registered.

Migration should be ordered.

Migration should be testable independently.

Migration should be idempotent.

Migration should never modify the original save in memory.

==================================================
Failure Handling
==================================================

Specify behaviour for:

Corrupted save

Missing save

Unknown version

Migration failure

Partial migration

Checksum mismatch (future)

Malformed data

User-facing behaviour must be documented.

Application must never crash because of invalid save data.
